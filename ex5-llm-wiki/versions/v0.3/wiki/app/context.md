# Системы — app

## Назначение

Алиса предлагает выделить контекст `app` для управления системами и реализацией изменений в их релизах. Разделение на контексты является предложением анализа, а не подтверждённым решением.[^email-02]

## Состав

- Сущность [«Приложение / система»](app.md): сведения о системе и назначение подразделения-владельца.
- Агрегат [«Релиз»](release.md): состав работ, состояние и результат выпуска, ссылки на реализуемые RFC.[^email-02]

Борис устанавливает, что изменения в системах реализуются в рамках релизов. Представление одного релиза как выпуска одной системы пока является допущением.[^email-01]

## Ответственность и взаимодействие

По предложению Алисы `app` ведёт системы, назначение их владельцев и релизы. Контекст [change](../change/context.md) ведёт подразделения и запросы. Для владельца системы используется ссылка на [подразделение](../change/org-unit.md), для работ релиза — ссылка на [RFC](../change/rfc.md). Между контекстами используются идентификаторы.[^email-02]

`app` получает сведения о подразделениях, запросах и затрагиваемых системах; передаёт сведения о включении работ в релиз и результатах реализации.[^email-02]

Алиса предлагает **Partnership** для совместного планирования и управления интеграцией и **Published Language** для документирования формата обмена. Партнёрство требует подтверждения взаимной зависимости поставки и ответственности команд. Состав сообщений и смысл состояний пока не определены.[^email-02]

## Вопросы для уточнения

- Подтверждается ли ограничение «один релиз — одна система»?
- Допускаются ли работы по нескольким RFC в одном релизе?
- Может ли реализация одного RFC в одной системе распределяться между несколькими релизами?
- Требуется ли отдельная координация общего выпуска нескольких систем?[^email-01]
